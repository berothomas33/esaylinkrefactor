رحلة العملية من زر البيع حتى نهايتها: البطاقة، والـ kernel، والبنك، ثم التأكيد أو الإلغاء عند البنك. كل اسم في الصفحة موجود في الكود، وكل سهم استدعاء حقيقي. الشرح كله على فرع transactionStepObserver.

1. المكوّنات: من يملك ماذا

لكل مسؤولية مالك واحد. الشاشة لا تعرف PAX، والـ EMV لا يعرف البنك ولا الـ threads، و PosTerminal هو الباب الوحيد الذي تدخل منه الشاشة.

2. العملية من البداية إلى النهاية

العملية تسير بخطواتها (TransactionSteps). كل خطوة تُنشر في Transaction.steps، و TransactionStepObserver هو المدخل الوحيد الذي يشغّل دالتها. ما ليس له دالة تقرير للشاشة فقط.

// TransactionStepObserver.onNext → dispatchTransactionStep(event)
switch (event.getStep()) {
    case TRANSACTION_STARTED: onTransactionStarted(event);   // → the transaction thread
    case CANCELLING:          onCancelling();                // stop the card search
    case ENDING:              onEnding();                    // the closings start
    case ACKNOWLEDGING:       onAcknowledging(event);        // tell the bank: done
    case REVERSING:           onReversing(event);            // ask the bank to reverse
    case CLOSING_COMPLETED:   onClosingCompleted(event);     // the next closing, or the end
    default:                  // a report: ONLINE_*, APPROVED, DECLINED, COMPLETED / ERROR / CANCELLED…
}

  • الانشغال: يُفحص على الـ main thread نفسه، فتُرفض عملية ثانية فورًا بـ TerminalBusyException، بلا طابور.
  • الإلغاء (Transaction.cancel()): تُضبط النهاية CANCELLED وتُنشر CANCELLING، فتتوقف قراءة البطاقة، ويتوقف الـ EMV عند أول goToStep. لا يُقاطَع الـ thread أبدًا.
  • إعادة المحاولة (fallback، tap again، See Phone): يطلبها الـ EMV بـ requestRetry(...) ثم يرجع الـ kernel، فيبدأ run محاولة جديدة من TERMINAL_INITIALIZATION، في العملية نفسها.
  • النتيجة ليست النهاية: APPROVED / DECLINED تُنشر فور معرفتها، أما COMPLETED فبعد التأكيد / الإلغاء عند البنك وتحرير الجهاز.
  • ترى الشاشة مثلًا: ONLINE_REQUIRED → ONLINE_PROCESSING → ONLINE_COMPLETED → APPROVED → ENDING → ACKNOWLEDGING → CLOSING_COMPLETED → COMPLETED.
  • ⚠ دالة الخطوة تعمل والـ lock مأخوذ، فترى الشاشة ACKNOWLEDGING / REVERSING بعد انتهاء نداء البنك (BACKLOG 10.4). لهذا تبقى الخطوات التي قد تنتظر البنك أو شخصًا قبل تحديد النهاية (ONLINE_PROCESSING، و Single Tap مستقبلًا) تقارير لا دوال.

3. خطوات الـ EMV: كيف يشغّل goToStep الدالة onXxx

لا يستدعي أحد onXxx مباشرة. goToStep(STEP) تنشر الخطوة على emvSteps، فيشغّل EmvStepObserver دالتها على الـ thread نفسه، وتنتهي قبل أن تعود goToStep. إن كانت العملية قد انتهت أو أُلغيت تُسقط الخطوة وتعيد goToStep القيمة false.

  • يجب أن يبقى التشغيل متزامنًا (بلا observeOn وبلا serialize): لو تأخرت الدالة إلى thread آخر لعادت goToStep قبل أن تعمل، فيرد askStep بـ "إلغاء" قبل أن تُفتح شاشة الـ PIN، وتتداخل استدعاءات native على kernel واحد.
  • الشاشة وحدها تستخدم observeOn(main) على emvSteps، لأنها تعرض الشريط فقط ولا ينتظرها أحد.

4. حين ينتظر الـ kernel شخصًا: askStep

أثناء استدعاء native (مثل EMVStartTrans) يتوقف الـ kernel ويسأل سؤالًا عبر callback: اختر التطبيق، أدخل الـ PIN. يجب أن يعود له ردٌّ دائمًا (setCallBackResult)، وإلا يبقى منتظرًا. الـ callback لا يفتح شاشة بنفسه؛ يسأل الخطوة المسؤولة عبر askStep.

5. الطريق إلى البنك

حين يرد الكارت بـ ARQC في الـ 1st GENERATE AC، ينتهي الاستدعاء الـ native ويرجع بالنتيجة RESULT_REQ_ONLINE. بعدها كودنا هو الذي يذهب إلى البنك، ثم يعود إلى الـ kernel بالـ 2nd GENERATE AC في خطوة أخرى. ثلاث طبقات، لكل منها اسمها:

كيف يعرف الـ EMV طريق البنك: attach

// BankRequest.java
public interface BankRequest { AuthResult send(TransactionConfig config); }

// AbstractEmvBehavior
private BankRequest bankRequest;
public final void attach(BankRequest bankRequest) { this.bankRequest = bankRequest; }
protected final void askTheBank() { bankAnswer = callTheBank(); }   // … bankRequest.send(config)
protected final AuthResult bankAnswer() { return bankAnswer; }      // read it, never ask again

// PosTerminal, in its constructor, once
behavior.attach(this::sendToBank);
  • لماذا attach وليس الـ constructor؟ دائرة: PosTerminal يحتاج الـ behavior في الـ constructor الخاص به، والـ behavior يحتاج PosTerminal::sendToBank الذي لا يوجد إلا بعده. فيُنشأ الـ behavior أولًا، ثم يوصّله PosTerminal بالبنك مرة واحدة (setter injection). Dagger لا يحل هذه الدائرة؛ حلّه هو attach نفسها خلف annotations.
  • الـ EMV لا يعرف PosTerminal: معه BankRequest فقط (Dependency Inversion). الـ field private و attach final، فلا يغيّر أحد الطريق ولا يتجاوز الفحوص.
  • نسختان من الرد، لكلٍّ مالك: bankAnswer() للـ EMV (ليكمل مع البطاقة، وتُمسح مع كل محاولة)، و OnlineRequest.answer لـ PosTerminal (ليقرر التأكيد أو الإلغاء). لا يقرأ أحدهما نسخة الآخر.
  • startOnlineProcess() ليست callback من الـ kernel: هي method في واجهات PAX (IContactCallback / IContactlessCallback) يناديها كودنا بعد أن يرجع الـ kernel. تبقى باسمها لأنها من الـ SDK.
  • الـ swipe والإدخال اليدوي لا kernel لهما: onReadApplicationData يذهب مباشرة إلى ONLINE_AUTHORIZATION، ثم TRANSACTION_COMPLETION يقرر من bankAnswer().

6. مسار الـ contact (بترتيب الـ kernel نفسه)

كل مرحلة = استدعاء native واحد = EmvStep واحدة. كل runContact* تستدعي الـ kernel: إن نجحت تنتقل بـ advanceContactStage(NEXT)، وإلا تنهي المسار بـ finishContactStage() (تحرير الـ listener، وإغلاق القارئات، وحساب النتيجة).

7. النتيجة والنهاية الآمنة

الـ EMV يبلّغ بالنتيجة (finishApproved / finishDeclined / finishError → Transaction.emvFinished)، والـ Transaction هي التي تنهي العملية. وقبل أن يصبح الجهاز متاحًا، يُغلق كل طلب أُرسل إلى البنك: تأكيد (acknowledgement) أو إلغاء (reversal).

8. مسار الـ contactless

طريقة التشغيل نفسها و askStep نفسها، لكن الـ kernel يُختار بعد اختيار التطبيق (ClssKernelProcessFactory). نوعان: granular (PayPass و PayWave و EFT) ولكل مرحلة استدعاء native مستقل، وatomic (Amex و JCB و Mir و PBOC و Pure و RuPay و DPAS) وفيها استدعاء واحد يعمل كل شيء.

9. الـ EMV params: مصدرها، ومكان حفظها، ومتى تصل إلى الـ kernel

الـ params هي ما يحتاجه الـ kernel ليقرر: البطاقات المقبولة (AIDs)، ومفاتيح التحقق من البطاقة (CAPKs)، والحدود المالية (مثل المبلغ الذي يُطلب بعده PIN).
