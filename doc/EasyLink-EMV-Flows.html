2. A sale from start to end

A sale runs on its own steps (TransactionStep). Every step enters through one method, publish, and is stored in Transaction.steps. TransactionStepObserver then runs the step's case in dispatchTransactionStep. A step with no case is only a report for the screen.

// TransactionStepObserver.onNext → dispatchTransactionStep(event)
switch (event.getStep()) {
  case TRANSACTION_STARTED: onTransactionStarted(event);
      // move to the transaction thread
  case CANCELLING: onCancelling();
      // stop the card search
  case APPROVED:   closeLast(ACKNOWLEDGING);
      // bank and card approved → acknowledge
  case DECLINED:   closeLast(REVERSING);
      // bank approved, card declined → reverse
  case ENDING:     onEnding();
      // reverse what is still open, free the terminal, deliver the end
  default:
      // a report: ONLINE_*, CARD_*, FAILED, the closings, the end
}

  • Busy. Checked on the caller's thread. A second sale is refused at once with TerminalBusyException; nothing is queued.
  • The state is the steps. There is no state field. The first decision step delivered is the state (decision()): CANCELLING, APPROVED, DECLINED or FAILED. No decision means the sale is running. The first decision wins; later ones are dropped.
  • The end follows the decision. CANCELLING → CANCELLED; APPROVED / DECLINED → COMPLETED; FAILED → ERROR with the same message. FAILED exists because ERROR must stay the last step.
  • Cancel. cancel() publishes CANCELLING. The card search stops, and the EMV stops at its next goToStep. The thread is never interrupted.
  • Retry (fallback, tap again, See Phone). The EMV calls requestRetry(...) and the kernel returns. run then starts a new attempt from TERMINAL_INITIALIZATION, in the same sale.
  • The result is not the end. APPROVED / DECLINED / FAILED are published as soon as they are known. COMPLETED comes later, after the bank is acknowledged or reversed and the terminal is free.
  • Nothing stays attached after the end (213762c):
    • The steps complete after the end (steps.onComplete()). Every subscriber is released without having to dispose. The steps stay readable, so a late subscriber still receives all of them.
    • run ends with forgetTransaction(). The EMV dispatcher is disposed, and the sale's data is cleared: the config (with field 55), the card, the bank answer.
    • emvSteps never completes. It belongs to the terminal, not to the sale; completing it would block the next sale. The screen listens to it per sale, until the sale ends (takeUntil).
  • A typical run on screen: ONLINE_REQUIRED → ONLINE_PROCESSING → ONLINE_COMPLETED → APPROVED → ACKNOWLEDGING → CLOSING_COMPLETED → ENDING → COMPLETED.
  • ⚠ The step cases run while the steps lock is held, including the bank calls of the closings. publish therefore checks the decision before taking the lock, so cancel() never waits for a closing. Steps that may wait for the bank or a person (ONLINE_PROCESSING, SINGLE_TAP_PIN_REQUIRED) stay reports, with no case.

3. EMV steps: how goToStep runs onXxx

Nobody calls an onXxx hook directly. goToStep(STEP) publishes the step on emvSteps. EmvStepObserver runs its hook on the same thread, and the hook finishes before goToStep returns. If the sale has ended or was cancelled, the step is dropped and goToStep returns false.

  • The dispatch must stay synchronous: no observeOn and no serialize on EmvStepObserver. The table below explains why.

4. When the kernel waits for a person: askStep

7. النتيجة والنهاية الآمنة

الـ EMV يبلّغ بالنتيجة (finishApproved / finishDeclined → publish(APPROVED / DECLINED)، و finishError → fail)، والـ Transaction هي التي تنهي العملية. وقبل أن يصبح الجهاز متاحًا، يُغلق كل طلب أُرسل إلى البنك: تأكيد (acknowledgement) أو إلغاء (reversal).

  • القرار نفسه يُغلق آخر طلب: case APPROVED → تأكيد، و case DECLINED → إلغاء، بشرط أن البنك وافق على آخر طلب (إن رفض البنك فلا شيء). في هذه اللحظة رد البنك معروف، والبطاقة قررت، والـ reader مغلق.

9. الـ EMV params: مصدرها، ومكان حفظها، ومتى تصل إلى الـ kernel

ما هي الـ params؟ هي القواعد التي يحتاجها الـ kernel ليتخذ قراره في كل عملية: البطاقات المقبولة (الـ AIDs)، والمفاتيح التي يُتحقَّق بها من أن البطاقة أصلية (الـ CAPKs)، والحدود المالية (مثل المبلغ الذي يُطلب بعده PIN في الدفع اللاتلامسي). بدونها لا يستطيع الـ kernel العمل.

دورة حياة الـ params في 5 خطوات

  • عند أول تشغيل للتطبيق: تُملأ قاعدة البيانات من ملفات JSON المرفقة بالتطبيق، حتى يكون هناك ما يعمل به. يحدث ذلك مرة واحدة فقط.
  • عند الضغط على Download: يرسل الـ host ملفًا (XML للـ contact وآخر للـ contactless)، فيُقرأ ويُكتب في قاعدة البيانات بدلًا من القديم.
  • قاعدة البيانات هي المصدر الأساسي: القيم الفعلية للـ params موجودة فيها.
  • الـ cache نسخة سريعة: أول عملية بعد أي تغيير تقرأ قاعدة البيانات كاملة مرة واحدة وتحتفظ بها في الذاكرة، والعمليات التالية تأخذ من الذاكرة مباشرة.
  • الـ kernel لا يحتفظ بشيء: في كل عملية تُحمَّل إليه الـ params من الـ cache من جديد، وتُمسح منه بانتهاء العملية.

مثال

غيّر الـ host حدّ طلب الـ PIN في الدفع اللاتلامسي من 600 إلى 1000 جنيه:

  • Download: أصبحت القيمة في قاعدة البيانات 1000، وأُفرِغ الـ cache.
  • أول عملية بعدها: يُعاد ملء الـ cache من قاعدة البيانات (1000)، ويستلمها الـ kernel.
  • عملية tap بمبلغ 800 جنيه: تتم دون طلب PIN ✓

ماذا تعرض شاشة EMV Params؟

  • DB: القيم المحفوظة (المصدر الأساسي).
  • Cached: القيم التي سيستلمها الـ kernel الآن. إن كانت فارغة فمعنى ذلك أنه لم تتم أي عملية منذ آخر تغيير، وليس أن هناك خطأ.

قواعد مهمة

  • الـ contact: إذا لم يتضمن ملف الـ host جزءًا معينًا، تبقى القيم القديمة كما هي. الـ contactless: ملف الـ host هو المرجع الكامل، وأي نوع بطاقة غير موجود فيه يُحذف.
  • بيانات الجهاز (TID، MID، MCC، اسم التاجر) لا تأتي من ملف الـ host.
  • ⚠ لا يوجد فحص لصلاحية الـ CAPKs: 76 من 88 في ملفات الـ JSON منتهية الصلاحية.
