2. A sale from start to end

A sale runs on its own steps (TransactionStep). Every step enters through one method, publish, and is stored in Transaction.steps. TransactionStepObserver then runs the step's case in dispatchTransactionStep. A step with no case is only a report for the screen.

// TransactionStepObserver.onNext → dispatchTransactionStep(event)
switch (event.getStep()) {
  case TRANSACTION_STARTED: onTransactionStarted(event);
      // move to the transaction thread
  case CANCELLING: onCancelling();
      // stop the card search
  case APPROVED:   closeLast(ACKNOWLEDGING);
      // bank and card approved → acknowledge
  case DECLINED:   closeLast(REVERSING);
      // bank approved, card declined → reverse
  case ENDING:     onEnding();
      // reverse what is still open, free the terminal, deliver the end
  default:
      // a report: ONLINE_*, CARD_*, FAILED, the closings, the end
}

  • Busy. Checked on the caller's thread. A second sale is refused at once with TerminalBusyException; nothing is queued.
  • The state is the steps. There is no state field. The first decision step delivered is the state (decision()): CANCELLING, APPROVED, DECLINED or FAILED. No decision means the sale is running. The first decision wins; later ones are dropped.
  • The end follows the decision. CANCELLING → CANCELLED; APPROVED / DECLINED → COMPLETED; FAILED → ERROR with the same message. FAILED exists because ERROR must stay the last step.
  • Cancel. cancel() publishes CANCELLING. The card search stops, and the EMV stops at its next goToStep. The thread is never interrupted.
  • Retry (fallback, tap again, See Phone). The EMV calls requestRetry(...) and the kernel returns. run then starts a new attempt from TERMINAL_INITIALIZATION, in the same sale.
  • The result is not the end. APPROVED / DECLINED / FAILED are published as soon as they are known. COMPLETED comes later, after the bank is acknowledged or reversed and the terminal is free.
  • Nothing stays attached after the end (213762c):
    • The steps complete after the end (steps.onComplete()). Every subscriber is released without having to dispose. The steps stay readable, so a late subscriber still receives all of them.
    • run ends with forgetTransaction(). The EMV dispatcher is disposed, and the sale's data is cleared: the config (with field 55), the card, the bank answer.
    • emvSteps never completes. It belongs to the terminal, not to the sale; completing it would block the next sale. The screen listens to it per sale, until the sale ends (takeUntil).
  • A typical run on screen: ONLINE_REQUIRED → ONLINE_PROCESSING → ONLINE_COMPLETED → APPROVED → ACKNOWLEDGING → CLOSING_COMPLETED → ENDING → COMPLETED.
  • ⚠ The step cases run while the steps lock is held, including the bank calls of the closings. publish therefore checks the decision before taking the lock, so cancel() never waits for a closing. Steps that may wait for the bank or a person (ONLINE_PROCESSING, SINGLE_TAP_PIN_REQUIRED) stay reports, with no case.

3. EMV steps: how goToStep runs onXxx

Nobody calls an onXxx hook directly. goToStep(STEP) publishes the step on emvSteps. EmvStepObserver runs its hook on the same thread, and the hook finishes before goToStep returns. If the sale has ended or was cancelled, the step is dropped and goToStep returns false.

  • Start. TERMINAL_INITIALIZATION prepares the kernel, then calls searchCard(), which starts SEARCH_CARD. If preparation fails, the sale ends with ERROR and no search runs.
  • The dispatch must stay synchronous: no observeOn and no serialize on EmvStepObserver. The table below explains why.
  • The screen is the exception. It may use observeOn(main) on emvSteps, because it only shows the banner and nothing waits for it. It subscribes per sale, so it can miss the first EMV step; the dispatch is not affected.

Why the dispatch must stay synchronous

observeOn(X) queues onNext and runs it later on another thread, so goToStep returns at once. On EmvStepObserver that breaks the flow:

4. When the kernel waits for a person: askStep

During one native call the kernel can stop and ask a question through a callback: choose the application, enter the PIN. It waits until it gets an answer (setCallBackResult). The callback does not open a screen itself: it asks the step that owns the question, with askStep. That step runs inside the step that called the kernel, and its answer goes back to the kernel, which carries on from where it stopped. This is the circle:

  • The circle is synchronous. Steps ①–⑨ run on the transaction thread, nested inside each other, and close from the inside out. askStep gets its answer before goToStep returns (§3). That is why the dispatch must never use observeOn.
  • Fail closed. No answer, a cancel or an exception → askStep answers USER_CANCEL at once. The kernel never waits forever and never approves without an answer.
  • Online PIN asks step 9 (CARDHOLDER_VERIFICATION): PIN pad + PIN key; the bank checks the PIN. Offline PIN asks step 10 (OFFLINE_PIN_VERIFICATION) directly (93a798a): PIN pad only; the kernel checks the PIN with the card.
  • Application selection is the same circle: EMVAppSelect → emvWaitAppSel → onWaitAppSelect → askStep(3 WAIT_ / 4 FINAL_APPLICATION_SELECTION) → a dialog, or the only application → the index back to the kernel.
  • Contactless has no PIN callback: the kernel returns first, then our code calls onCardHolderPwd(true, …) itself when the CVM is online PIN (and again for Single Tap, §8). Same askStep, same hook.

  • Two copies of the answer, each with one owner. bankAnswer() is the EMV's: it carries on with the card, and is cleared at each attempt. OnlineRequest.answer is the terminal's: it decides the acknowledgement or the reversal. Neither reads the other's copy.
  • askTheBank always keeps its answer, even when it returns early (no field 55, or a cancel), so the vendor reads the real reason.
  • Swipe and manual entry have no kernel: onReadApplicationData goes straight to ONLINE_AUTHORIZATION, and the result comes from bankAnswer() (finishNonEmv).
  • startOnlineProcess() is never called. It is part of PAX's callback interfaces, but neither the kernel nor our code calls it; going online is the ONLINE_AUTHORIZATION step. It stays only because the interface requires it.

How the EMV reaches the bank: attach

The EMV must call the bank, but must not know PosTerminal. So PosTerminal gives it one thing to call, a BankRequest, once, when it is created:

// BankRequest.java
public interface BankRequest { AuthResult send(TransactionConfig config); }

// AbstractEmvBehavior
private BankRequest bankRequest;
public final void attach(BankRequest bankRequest) {
    this.bankRequest = bankRequest;
}
protected AuthResult askTheBank() {
    … return bankAnswer = bankRequest.send(config);

// PosTerminal constructor, once
behavior.attach(this::sendToBank);

Why not pass it in the constructor? The two objects need each other. PosTerminal needs the behavior in its constructor, and the behavior needs PosTerminal::sendToBank, which exists only after PosTerminal is built. So the behavior is built first, and wired to the bank right after:

7. The outcome and the safe end

The EMV reports the outcome (finishApproved / finishDeclined → publish(APPROVED / DECLINED); finishError → fail). The Transaction ends the sale. Before the terminal is free again, every request sent to the bank is closed: acknowledged or reversed.

Who closes what

  • The decision closes the last request. case APPROVED acknowledges it and case DECLINED reverses it, but only if the bank approved it. At that moment the bank's answer is known, the card has decided, and the reader is closed.
  • ENDING closes the rest. Every request with no ACKNOWLEDGING / REVERSING step carrying its id is reversed if the bank may have approved it (approved, failed, no answer). This covers a cancel (it can arrive while the bank is still answering), FAILED, and requests from an earlier attempt. Then the terminal is freed and the end is delivered.
  • The id links them. sendToBank names each request (asyncRequestId) and records it with its answer (wentOnline) before sending. A Single Tap resend is the same request, so it is closed once.

9. EMV params: where they come from, where they live, when they reach the kernel

What they are. The rules the kernel needs to decide each sale: which cards are accepted (AIDs), the keys that prove a card is genuine (CAPKs), and the amount limits (for example, the amount above which a contactless sale asks for a PIN). Without them the kernel cannot run.

  1. First start. The database is filled once from the JSON files in the app, so there is something to work with.
  2. Download. The host sends one XML for contact and one for contactless. They are parsed and written over the old values.
  3. The database is the source of truth. The real values live there.
  4. The cache is a fast copy. The first sale after a change reads the whole database once; later sales read memory.
  5. The kernel keeps nothing. Every attempt loads the params from the cache again.

Example. The host raises the contactless PIN limit from 600 to 1000 EGP. Download writes 1000 and empties the cache. The next sale reloads the cache (1000) and hands it to the kernel. A tap for 800 EGP now goes through with no PIN.

Rules

  • Contact: what the host file does not bring keeps its old value. Contactless: the host file is the whole truth; a kernel it does not bring is deleted (DPAS, EFT, JCB, Mir, PBOC, Pure, RuPay always: no parser).
  • Terminal identity (TID, MID, MCC, merchant name) does not come from the host file (OTHERCONFIGURATION is skipped on purpose).
  • EMV Params screen: DB shows the stored values; Cached shows what the kernel gets now. An empty cache means no sale since the last change, not an error.
  • ⚠ CAPKs are not checked (expiry, checksum): 76 of the 88 seed CAPKs have expired. A CAPK with no valid RID or key id is skipped.
  • 5755adb restored the 12 missing setXxxParam calls in loadFromDatabase (the preTransProcess crash); EmvParamServiceCacheTest guards it.

11. Using us as an SDK (an app integrating us)

The idea: any app uses us for the card and EMV part. The simplest contract: the app gives us its bank and listens to the steps. dispatchTransactionStep (acknowledge and reverse) stays inside; the app never writes it.

DirectionWhatHow
App → usThe bankImplements CommunicationBehavior: connectToHost(request) is required (send the sale, return an AuthResult); acknowledge / reverse are optional. The request arrives already named (request.getAsyncRequestId()).
App → usPrinting (optional)PrinterBehavior.print(lines)
Us → appThe stepstransaction.steps(): APPROVED / DECLINED / FAILED, then the end COMPLETED / ERROR / CANCELLED (terminal free); the rest is progress. The stream completes after the end.
App → usStart and cancelpos.acceptCard(type, amount), transaction.cancel()
 
// the integrator's bank — the only code they must write for the EMV part
class MyBank implements CommunicationBehavior {
    // required: send the sale, return the answer
    public Single<AuthResult> connectToHost(TransactionConfig request) { … }
    // optional
    public Completable acknowledge(TransactionConfig sent) { … }
    public Completable reverse(TransactionConfig sent) { … }
}

// their own screen (level B): start, observe, cancel
Transaction t = pos.acceptCard(TransactionType.SALE, amountMinor);
t.steps().subscribe(e -> {
    switch (e.getStep()) {
        case APPROVED:  /* approved + receipt fields */ break;
        case DECLINED:  /* declined */ break;
        case FAILED:    /* the error */ break;
        case COMPLETED:
        case ERROR:
        case CANCELLED: /* done, terminal free */ break;
        default:        /* progress: CARD_READ, ONLINE_* … */ break;
    }
});
cancelButton.setOnClickListener(v -> t.cancel());
  • Why our switch stays inside: it protects the money. Acknowledge when the card approves, reverse when it declines, and reverse in ENDING after a cancel or a failure (a cancel can arrive while the bank is still answering). If every app wrote it, one would forget the reversal after a cancel and the customer would be charged. Inside, it is written once and covered by tests.
  • The request id is ours: sendToBank names the request (asyncRequestId) before the app sees it; the acknowledgement and reversal carry the same id. The EMV never sees it.
  • The switch in the app's code above is for its screen only; it does not drive the sale.
