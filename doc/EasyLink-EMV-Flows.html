2. العملية من البداية إلى النهاية

العملية تسير بخطواتها (TransactionSteps). كل خطوة تُنشر في Transaction.steps، و TransactionStepObserver هو المدخل الوحيد الذي يشغّل دالتها. ما ليس له دالة تقرير للشاشة فقط.

// TransactionStepObserver.onNext → dispatchTransactionStep(event)
switch (event.getStep()) {
    case TRANSACTION_STARTED: onTransactionStarted(event);   // → the transaction thread
    case CANCELLING:          onCancelling();                // stop the card search
    case ENDING:              onEnding();                    // the closings start
    case ACKNOWLEDGING:       onAcknowledging(event);        // tell the bank: done
    case REVERSING:           onReversing(event);            // ask the bank to reverse
    case CLOSING_COMPLETED:   onClosingCompleted(event);     // the next closing, or the end
    default:                  // a report: ONLINE_*, APPROVED, DECLINED, COMPLETED / ERROR / CANCELLED…
}

  • الانشغال: يُفحص على الـ main thread نفسه، فتُرفض عملية ثانية فورًا بـ TerminalBusyException، بلا طابور.
  • الإلغاء (Transaction.cancel()): تُضبط النهاية CANCELLED وتُنشر CANCELLING، فتتوقف قراءة البطاقة، ويتوقف الـ EMV عند أول goToStep. لا يُقاطَع الـ thread أبدًا.
  • إعادة المحاولة (fallback، tap again، See Phone): يطلبها الـ EMV بـ requestRetry(...) ثم يرجع الـ kernel، فيبدأ run محاولة جديدة من TERMINAL_INITIALIZATION، في العملية نفسها.
  • النتيجة ليست النهاية: APPROVED / DECLINED تُنشر فور معرفتها، أما COMPLETED فبعد التأكيد / الإلغاء عند البنك وتحرير الجهاز.
  • ترى الشاشة مثلًا: ONLINE_REQUIRED → ONLINE_PROCESSING → ONLINE_COMPLETED → APPROVED → ENDING → ACKNOWLEDGING → CLOSING_COMPLETED → COMPLETED.
  • ⚠ دالة الخطوة تعمل والـ lock مأخوذ، فترى الشاشة ACKNOWLEDGING / REVERSING بعد انتهاء نداء البنك (BACKLOG 10.4). لهذا تبقى الخطوات التي قد تنتظر البنك أو شخصًا قبل تحديد النهاية (ONLINE_PROCESSING، و Single Tap مستقبلًا) تقارير لا دوال.

9. الـ EMV params: مصدرها، ومكان حفظها، ومتى تصل إلى الـ kernel

ما هي الـ params؟ هي القواعد التي يحتاجها الـ kernel ليتخذ قراره في كل عملية: البطاقات المقبولة (الـ AIDs)، والمفاتيح التي يُتحقَّق بها من أن البطاقة أصلية (الـ CAPKs)، والحدود المالية (مثل المبلغ الذي يُطلب بعده PIN في الدفع اللاتلامسي). بدونها لا يستطيع الـ kernel العمل.

دورة حياة الـ params في 5 خطوات

  • عند أول تشغيل للتطبيق: تُملأ قاعدة البيانات من ملفات JSON المرفقة بالتطبيق، حتى يكون هناك ما يعمل به. يحدث ذلك مرة واحدة فقط.
  • عند الضغط على Download: يرسل الـ host ملفًا (XML للـ contact وآخر للـ contactless)، فيُقرأ ويُكتب في قاعدة البيانات بدلًا من القديم.
  • قاعدة البيانات هي المصدر الأساسي: القيم الفعلية للـ params موجودة فيها.
  • الـ cache نسخة سريعة: أول عملية بعد أي تغيير تقرأ قاعدة البيانات كاملة مرة واحدة وتحتفظ بها في الذاكرة، والعمليات التالية تأخذ من الذاكرة مباشرة.
  • الـ kernel لا يحتفظ بشيء: في كل عملية تُحمَّل إليه الـ params من الـ cache من جديد، وتُمسح منه بانتهاء العملية.

مثال

غيّر الـ host حدّ طلب الـ PIN في الدفع اللاتلامسي من 600 إلى 1000 جنيه:

  • Download: أصبحت القيمة في قاعدة البيانات 1000، وأُفرِغ الـ cache.
  • أول عملية بعدها: يُعاد ملء الـ cache من قاعدة البيانات (1000)، ويستلمها الـ kernel.
  • عملية tap بمبلغ 800 جنيه: تتم دون طلب PIN ✓

ماذا تعرض شاشة EMV Params؟

  • DB: القيم المحفوظة (المصدر الأساسي).
  • Cached: القيم التي سيستلمها الـ kernel الآن. إن كانت فارغة فمعنى ذلك أنه لم تتم أي عملية منذ آخر تغيير، وليس أن هناك خطأ.

قواعد مهمة

  • الـ contact: إذا لم يتضمن ملف الـ host جزءًا معينًا، تبقى القيم القديمة كما هي. الـ contactless: ملف الـ host هو المرجع الكامل، وأي نوع بطاقة غير موجود فيه يُحذف.
  • بيانات الجهاز (TID، MID، MCC، اسم التاجر) لا تأتي من ملف الـ host.
  • ⚠ لا يوجد فحص لصلاحية الـ CAPKs: 76 من 88 في ملفات الـ JSON منتهية الصلاحية.
