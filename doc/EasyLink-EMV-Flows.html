PosTerminal هو الجهاز نفسه

يمثّل PosTerminal جهاز نقطة البيع الذي يستخدمه الكاشير، أيًّا كان نوعه (PAX A920، Ingenico…). لكل جهاز الأجزاء نفسها، ولكل جزء field في الكود:

// PosTerminal = the POS machine
protected final AbstractEmvBehavior   behavior;       // the card: EMV with the card (search + reader + kernel)
protected final CommunicationBehavior communication;  // HTTP to the bank / the facilitator
protected final PrinterBehavior       printer;        // the printer: the receipt
private   final Scheduler             transactionScheduler; // one sale at a time, one thread
البطاقة ← EmvBehaviorيتعامل مع البطاقة: يبحث عنها، ويقرؤها، وينفّذ خطوات الـ EMV مع الـ kernel، ويجهّز الطلب للبنك. لكل vendor واحد (PaxEmvBehavior).
البنك ← CommunicationBehaviorالاتصال بالبنك أو الـ facilitator عبر HTTP: authorize (البيع / الاسترداد)، ثم بعد تحديد النتيجة acknowledge أو reverse. التطبيق الحالي: SaleCommunicationBehavior.
الطابعة ← PrinterBehaviorتطبع الإيصال على thread مستقل، بالترتيب. على PAX: PaxPrinter.
الجهاز نفسهينفّذ عملية واحدة في كل مرة (thread واحد، و current تعني أنه مشغول)، ويشغّل الـ EMV (behavior.run، والبحث عن البطاقة بداخله)، ويربط هذه الأجزاء معًا.

2. بداية العملية ونهايتها

يجري فحص الانشغال على الـ main thread نفسه (compareAndSet)، فتُرفض أي عملية ثانية فورًا بـ TerminalBusyException، دون أي طابور انتظار.

تسير العملية بخطواتها الخاصة (TransactionSteps): عند نشر الخطوة تُنفَّذ الدالة الخاصة بها فورًا وعلى الـ thread نفسه، كما هو الحال في خطوات الـ EMV. كل خطوة تقود العملية لها حالة في dispatchTransactionStep:

switch (event.getStep()) {
    case TRANSACTION_STARTED: onTransactionStarted(event); // to its thread
    case CANCELLING:          onCancelling();              // search stops
    case ACKNOWLEDGING:       onAcknowledging(event);      // host: sale done
    case REVERSING:           onReversing(event);          // host: reverse
    case APPROVED, DECLINED:  onOutcome(event);            // decides the end
    case COMPLETED, ERROR,
         CANCELLED:           onEnd();                     // the safe end
    default:                  // a report (ONLINE_*, CARD_READ…)
}

الخطوة العادية تُسلَّم ثم تُشغَّل دالتها. واستثناءان تسلّمهما دالتهما بنفسها: النتيجة (مع النهاية في مسكة واحدة للـ lock، فلا يقع إلغاء بينهما) والنهاية (بعد أن يصبح الجهاز متاحًا). أما ONLINE_* فتقارير، لأن authorize تعيد رد الـ host مباشرة إلى الـ kernel من أجل الـ 2nd GENERATE AC.

نسخة الـ Rx (الفرع transactionStepObserver، الفرق الوحيد عن هذا الكود): الـ switch نفسه يستدعيه TransactionStepObserver مشترك في الـ steps، كما يفعل EmvStepObserver في الـ EMV. يبقى الـ lock، وتقرأ publish / end / cancel قيمة end قبل دخوله، فلا ينتظر الإلغاء الـ ack. الثمن المقبول: ترى الشاشة ACKNOWLEDGING / REVERSING بعد انتهاء نداء الـ host لا قبله (BACKLOG 10.4). ولم يعد الـ dispatch هو الفرق الوحيد: في هذا الفرع أيضًا ENDING وسلسلة الإغلاق (§7)، والأسماء الجديدة للطريق إلى البنك (§5)، والـ network بخطوات متتالية ومهلة 25 ثانية لكل نداء؛ القائمة كاملة في doc/REFERENCE.md §10.

الـ EMV كله داخل behavior.run: البحث عن البطاقة (SEARCH_CARD) وإعادة المحاولة، كما يفعل الـ Entry Point في EMV Book B. ونهاية العملية آمنة: يُرسَل التأكيد أو الإلغاء إلى الـ host ويُنتظر رده قبل أن يصبح الجهاز متاحًا لعملية جديدة. (تعديلات 28/10، لم تُختبر على الجهاز بعد.)

9. الـ EMV params: مصدرها، ومكان حفظها، ومتى تصل إلى الـ kernel

ما هي الـ params؟ هي القواعد التي يحتاجها الـ kernel ليتخذ قراره في كل عملية: البطاقات المقبولة (الـ AIDs)، والمفاتيح التي يُتحقَّق بها من أن البطاقة أصلية (الـ CAPKs)، والحدود المالية (مثل المبلغ الذي يُطلب بعده PIN في الدفع اللاتلامسي). بدونها لا يستطيع الـ kernel العمل.

دورة حياة الـ params في 5 خطوات

  • عند أول تشغيل للتطبيق: تُملأ قاعدة البيانات من ملفات JSON المرفقة بالتطبيق، حتى يكون هناك ما يعمل به. يحدث ذلك مرة واحدة فقط.
  • عند الضغط على Download: يرسل الـ host ملفًا (XML للـ contact وآخر للـ contactless)، فيُقرأ ويُكتب في قاعدة البيانات بدلًا من القديم.
  • قاعدة البيانات هي المصدر الأساسي: القيم الفعلية للـ params موجودة فيها.
  • الـ cache نسخة سريعة: أول عملية بعد أي تغيير تقرأ قاعدة البيانات كاملة مرة واحدة وتحتفظ بها في الذاكرة، والعمليات التالية تأخذ من الذاكرة مباشرة.
  • الـ kernel لا يحتفظ بشيء: في كل عملية تُحمَّل إليه الـ params من الـ cache من جديد، وتُمسح منه بانتهاء العملية.

مثال

غيّر الـ host حدّ طلب الـ PIN في الدفع اللاتلامسي من 600 إلى 1000 جنيه:

  • Download: أصبحت القيمة في قاعدة البيانات 1000، وأُفرِغ الـ cache.
  • أول عملية بعدها: يُعاد ملء الـ cache من قاعدة البيانات (1000)، ويستلمها الـ kernel.
  • عملية tap بمبلغ 800 جنيه: تتم دون طلب PIN ✓

ماذا تعرض شاشة EMV Params؟

  • DB: القيم المحفوظة (المصدر الأساسي).
  • Cached: القيم التي سيستلمها الـ kernel الآن. إن كانت فارغة فمعنى ذلك أنه لم تتم أي عملية منذ آخر تغيير، وليس أن هناك خطأ.

قواعد مهمة

  • الـ contact: إذا لم يتضمن ملف الـ host جزءًا معينًا، تبقى القيم القديمة كما هي. الـ contactless: ملف الـ host هو المرجع الكامل، وأي نوع بطاقة غير موجود فيه يُحذف.
  • بيانات الجهاز (TID، MID، MCC، اسم التاجر) لا تأتي من ملف الـ host.
  • ⚠ لا يوجد فحص لصلاحية الـ CAPKs: 76 من 88 في ملفات الـ JSON منتهية الصلاحية.
